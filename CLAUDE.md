## Core conventions

- Indentation: tabs by default (`.editorconfig`), but match the file you are in. 17 files are 4-space only: 5 of the 28 `dim/*/genlayer/*` files (the other 23 use tabs), `handler/ae2/MSUExternalStorageHandler`, `handler/ae2/MassStorageMEInventory`, `world/ModBiomes`, `inventory/gui/GuiInfoContainerLayered`, `render/loader/HmfModelLoader` and others. About 54 more are mostly spaces with some tab lines (e.g. `handler/CompatHandler.java`, `handler/atmosphere/ChunkAtmosphereManager.java`, `handler/ae2/AE2CompatHandler.java`, `entity/item/EntityMinecartModBase.java`, `render/loader/HbmModelObject.java`).
- Line endings: everything is LF in the repository since `27811a59` (582 upstream CRLF files normalised, content-identical). `.gitattributes` declares every text type `text eol=lf` (`*.bat` checks out as CRLF, binaries `-text`), so git normalises on commit, and `.editorconfig` says `lf`. Upstream still ships CRLF files, so every merge from `upstream`/`hbm` must run with `-Xrenormalize` (`git config merge.renormalize true` once per clone makes it the default); without it every CRLF file upstream touched conflicts wholesale. `-Xrenormalize` only normalises files both sides changed: files upstream added and files only upstream changed (including its CRLF flips) enter the index exactly as upstream committed them, so merge with `--no-commit` and run `git add --renormalize .` before committing. Never re-introduce CRLF; `tools/check-fork.sh` fails if the index contains any. `git blame` skips the normalisation via `.git-blame-ignore-revs` (`git config blame.ignoreRevsFile .git-blame-ignore-revs` once per clone; both settings are already made in the owner's local clone). The owner's Windows working tree is still CRLF on disk for about 4800 files (Git for Windows sets `core.autocrlf=true` system-wide, and git does not rewrite unchanged files when attributes change); that is harmless because commits normalise to LF, but check endings with `git ls-files --eol` (the `i/` and `w/` columns) or Python, not `grep $'\r'` under Git Bash, which gives false positives. Eleven tracked text files match no `.gitattributes` rule (`.editorconfig`, `.git-blame-ignore-revs`, `.gitattributes`, `.gitignore`, `LICENSE`, `LICENSE.LESSER`, `changelog`, `curseforge.properties.example`, `models/doors/seal.dae`, `models/weapons/tom_flame.hmf`, `sounds/misc/desktop.ini`).
- Style: `if(cond)` and `for(` without a space, braces on the same line, obfuscated MCP names (`func_147480_a`) left as-is, informal comments.
- Logging: `MainRegistry.logger` (the Log4j logger `HBM`, created by a static initialiser at `MainRegistry.java:121`; the `event.getModLog()` fallback in `preInit`, L683-684, never runs because the field is never null, B-010) is the only logger, with the subsystem in brackets (`[QMAW]`, `[Jigsaw]`, `[Debug]`). Do not create loggers or add `System.out.println` (62 legacy calls remain).
- Translation: use `com.hbm.util.i18n.I18nUtil` (`resolveKey`, `resolveKeyArray`, `format`), never `net.minecraft.client.resources.I18n` (it is `@SideOnly(Side.CLIENT)`, so common code that touches it breaks the dedicated server; 343 legacy direct calls remain). On the dedicated server `I18nUtil` returns "I18N CALL SERVERSIDE - GREAT JOB"; server text uses `ChatBuilder`/`ChatComponentTranslation`.
- Side discipline: common code reaches the client only through `MainRegistry.proxy` virtuals (`ServerProxy` no-op base, `ClientProxy` override). `@SideOnly(Side.CLIENT)` on client-only methods (`provideGUI`, `getMaxRenderDistanceSquared`, render helpers). Never reference `ResourceManager`, `IItemRenderer`, `ModelBiped` or `AnimatedModel` from static fields or constructors of common classes.
- Tick split: TE logic under `if(!worldObj.isRemote)`, then `networkPackNT(range)` (block radius of the `TargetPoint`: 15-50 for single-block tiles, 100-150 for multiblocks, 250 for the largest; `serialize` runs every tick, keep it small); the client branch only does animation and audio. Sync fields via `serialize(ByteBuf)`/`deserialize(ByteBuf)` in identical order, calling `super` first.
- Edit policy (owner decision, 2026-09-25): there are no restrictions on what may be edited. Every file in the repository may be changed, whether it came from upstream or is fork-owned: registries (`ModItems`, `ModBlocks`, `TileMappings`, `ClientProxy`, `MainRegistry`), recipe classes, lang files, assets, `changelog`, `README.md`, `gradle.properties`, `RefStrings`, `build.gradle`, CI, `.editorconfig`, the vendored `cofh` API, the docs and the tooling. Refactors, deletions, renames and new libraries are allowed. DBS is a personal fork with no upstream pull requests planned (`CONTRIBUTING.md` was removed in `ea346f74`), so upstream's rules (no refactors, no new libraries, no AI-written code) do not apply either. This supersedes any older wording that restricts edits wherever it still appears: the rewritten `docs/` have dropped the former "small diffs by default" and "fixes go through the fork-owned package" rules (`docs/fork-notes.md` quotes them only as history), and the "rather than inline in an upstream file" wording in the `DBSFork.java` javadoc also predates this policy.
- What still applies is technical, not a restriction on what to touch: the registration-order and persisted-ID rules below, side discipline, `serialize`/`deserialize` order, LF line endings, `I18nUtil` over `I18n`, testing on client and dedicated server, and optional mods (OC, NEI, AE2; none is bundled in the jar) staying behind `Loader.isModLoaded` / `@Optional` so the jar still loads without them. The working agreement on commits (below) is unchanged.
- Merge cost is a trade-off, not a rule: while the fork keeps merging JameH2's branch, an edit in a file upstream also changes can conflict (hotspots in `docs/fork-notes.md`), whereas code in `com/hbm/dbs/` never does. Pick whichever is cleaner for the change at hand; a large rework of an upstream file is fine when it pays for itself. For fixes from the tracker, keep the `// DBS fix B-xxx` marker: it is a tracking aid that lets `tools/check-fork.sh` notice a merge that undid a fix, not a limit on the edit.
- Registration lives in `MainRegistry` (`PreLoad` -> `load` -> `PostLoad`) and is order-dependent: append a new registration at the END of the block that already holds its kind (full chain in `docs/codebase-map.md` area 1; what runs before and after the `DBSFork.init()` hook is in `docs/extending.md`). Hazard classes and rad resistance are filled in `PostLoad` (`ArmorUtil.register()` ~L600, `HazmatRegistry.registerHazmats()` ~L601) from entries that `ArmorFSB` pieces queue when they are constructed, so armor must be constructed before `PostLoad`: upstream armor in `ModItemsArmor.init()`, fork armor there or from the `DBSFork.init()` hook. The tables are not frozen afterwards: later writes win, earlier direct writes to the same key are overwritten there, and an existing `hbmRadResist.json` replaces the rad-resistance table wholesale.
- Persisted positional values, append only, never insert or reorder (saved to disk): `EnumAmmo` ordinals and every other `ItemEnumMulti`/`BlockEnumMulti` enum (item damage, block meta), `BulletConfig` ids (creation order across `XFactory` init; stored in gun NBT), weapon-mod ids (`WeaponModBase`; HashBiMap silently overwrites duplicate ids), `SolarSystem.Body` ordinals (ore meta, max 16), `XSatelliteRegistry` ids, `SiegeTier` ids, Fluids IDs, `Mats` material ids, `ItemMold` ids, spawn-egg ids (`ModEntityList`, first free from 500, stored as vanilla egg damage); `GenericRecipe` names are persisted by string in machine NBT. Positional but only synced (client and server must run the same jar): packet discriminators (`PacketDispatcher`), `CelestialBodyTrait` indices (saves use the trait name), mod-entity ids, `EnumKeybind`. `docs/extending.md` has the full table with current maxima and proposed fork ID bands.
- Lang keys: `item.<unloc>.name`, `tile.<name>.name`, `.desc` with `$` as the line break (all other key families in `docs/codebase-map.md` area 17). Edit `en_US.lang` (LF); mirror to `zh_CN`/`ru_RU` when practical. A literal `%` must be written `%%` only in keys resolved through a formatting call (`I18nUtil`, `ChatComponentTranslation`); `.name` keys are shown unformatted (`StatCollector.translateToLocal`), so use a plain `%` there (codebase-map area 17).
- `changelog` may be edited (fork notes under `## Added`/`## Changed`/`## Fixed`). Know that it is the release text of the CurseForge upload task in `build.gradle` (active only when `curseforge.properties` exists), which moves it to `changelog.bak` and leaves an empty file after uploading, and that upstream rewrites it on most merges.
- Editing the version and meta files is allowed; technical couplings to keep in mind: CI seds `RefStrings.VERSION` and `mod_build_number`. The VERSION sed matches `public static final String VERSION = "...";` (keep that shape) and replaces the whole value with the literal `1.0.27 BETA (<days>)`, so a fork-specific VERSION or a `mod_version` bump also needs that literal changed in `.github/workflows/build.yml`, or every CI jar reverts to `1.0.27 BETA`. `build.gradle` forms the jar version from `gradle.properties` plus the `_H261` suffix, and `HTTPHandler`'s update check compares `RefStrings.VERSION` with JameH2's repository (so a fork-specific version always reads as outdated until the check is repointed; tracker B-008). `.editorconfig` carries one fork line, `end_of_line = lf`. Reordering registry lists (`ModItems`, `ModBlocks`, `TileMappings`, `ClientProxy`) does not break saves but makes upstream merges painful; the positional lists in the persisted-ID rule above are a different matter.
- Existing fork code lives in `src/main/java/com/hbm/dbs/`, plus one restored class outside it: `handler/nei/BreederRecipeHandler.java` (upstream deleted it in `804d2bd1`, `50db588d` re-added it byte-identical, and `tools/check-fork.sh` checks it as fork-owned). `DBSFork.init()` is the entry point, called from the `// DBS fork hook` line in `MainRegistry.PreLoad` directly after `ModItems.mainRegistry()` (it must run after `ModItems.mainRegistry()` and before `PostLoad`; `tools/check-fork.sh` checks only that the hook line comes after `ModItems.mainRegistry()` in `MainRegistry.java`, not that it stays inside `PreLoad`); `DBSRecipes` is an `IRecipeRegisterListener` whose `onRecipeLoad` adds the restored recipes when `SerializableRecipe.initialize()` reports `AssemblyMachineRecipes` or `AnvilRecipes` (same JSON-override semantics as an inline default); `DBSItems` re-applies creative tabs. Other fork changes to upstream files: the marked `BreederRecipeHandler` registration in `NEIRegistry`, the " (LEGACY)"-stripping lang edits in `en_US.lang`/`de_DE.lang` (plus a dead de_DE key `tile.machine_reactor_on.name`), `.editorconfig` line 5 (`end_of_line = lf`) and the deleted `CONTRIBUTING.md`. The package is a convenience, not a requirement: new fork work can go there or inline in upstream files, and existing fork code can be moved inline. If the restored recipes move out of `DBSRecipes`, update the duplicate-recipe checks in `tools/check-fork.sh`: a duplicate `GenericRecipes` id throws inside `GenericRecipes.register` after it has already appended the recipe to the ordered list, and `DBSRecipes.onRecipeLoad` catches and logs that, so the machine gets a duplicate entry and the remaining fork recipes of that set are skipped. Upstream's `@Deprecated` markers are inert; removing them is allowed (keeping them avoids a merge conflict). After every upstream merge run `bash tools/check-fork.sh` from the repo root (Git Bash on Windows) and fix every `MISS` before building; the script is LF like the whole tree.
- Marker annotations from `com.hbm.interfaces`: `@Spaghetti("why")` for known-bad code, `@Untested`, `@NotableComments`; keep them when editing. `@Deprecated` is used liberally on still-live legacy paths; check callers before deleting anything.
- Working agreement (details in `docs/fork-notes.md`): either the owner or a session makes code changes. ## How-to checklists

Full recipes with exemplar paths are in `docs/codebase-map.md`; the four most common tasks are inlined here.

Add an item:
1. Declare `public static Item x;` in `src/main/java/com/hbm/items/ModItems.java`.
2. Instantiate in `initializeItem()`: `new Item().setUnlocalizedName("x").setCreativeTab(MainRegistry.partsTab).setTextureName(RefStrings.MODID + ":x")`; use `ItemCustomLore` for `.desc` tooltips, `ItemEnumMulti(Enum.class, true, true)` for meta variants.
3. Add `GameRegistry.registerItem(x, x.getUnlocalizedName());` in `registerItem()` (forgetting this silently makes it unobtainable; 6 items already suffer this, tracker B-115/B-116).
4. Texture `assets/hbm/textures/items/x.png` (enum: `x.<enum_lower>.png`); lang `item.x.name` (enum: `item.x.<enum_lower>.name`).
5. Hazards in `hazard/HazardRegistry.registerItems` (fuel helpers such as `registerRBMKRod`/`registerRTGPellet` are private to that class); ore dict in `inventory/OreDictManager`.
Exemplar: `src/main/java/com/hbm/items/special/ItemExpensive.java`.

Add a block:
1. Declare in `blocks/ModBlocks.java`; fluent chain in `initializeBlock()` ending in `.setBlockTextureName(RefStrings.MODID + ":x")` (mandatory for bases that do not extend `BlockBase`, e.g. `BlockOre`, `BlockHazard`, `BlockDummyable`).
2. `register(x);` in `registerBlock()` to get `ItemBlockBase`. The 2-arg `GameRegistry.registerBlock` gives a vanilla ItemBlock and silently drops `ITooltipProvider`/`IBlockMulti`/`IPersistentInfoProvider`.
3. Texture `textures/blocks/x.png`; lang `tile.x.name` (+ `tile.x.desc`).
4. Registry name is `hbm:tile.<name>`; renames need `ModBlocks.addRemap("<old name>", newBlock, meta)` in `registerBlock()`. `MainRegistry.handleMissingMappings` only ignores names or remaps items (it has no BLOCK branch), so it cannot handle a block rename until such a branch is added (B-046).
Exemplar: `src/main/java/com/hbm/blocks/generic/BlockGeneric.java`; enum subtypes: `generic/BlockMeteorOre.java`.
From fork code outside the registries, the same steps use public entry points instead: `GameRegistry.registerItem(x, x.getUnlocalizedName())`; `GameRegistry.registerBlock(b, ItemBlockBase.class, b.getUnlocalizedName())` (`ModBlocks.register` is private, and the unlocalized name keeps the `hbm:tile.<name>` registry name); and for a TE everything the private `TileMappings.put` does: `TileMappings.map.put(TE.class, new String[]{"tileentity_x"})`, `TileMappings.configurables.add(TE.class)` for an `IConfigurableMachine`, and `Compat.blacklistAccelerator(TE.class)` (all public; `map` and `configurables` are read after the `DBSFork.init()` hook); `docs/extending.md` covers each content kind, including fluids, packets and entities, whose upstream how-tos below assign positional ids that shift or collide once upstream appends its own.

Add a machine end-to-end:
1. Block `extends BlockDummyable`: `createNewTileEntity` returns the core TE for `meta >= 12`, `new TileEntityProxyCombo().inventory().power().fluid()` for `meta >= 6`, else null; `getDimensions()` = {U, D, N, S, W, E} in the SOUTH-facing frame; `getOffset()`; override `fillSpace` to call super then `makeExtra` on ports after `x += dir.offsetX * o; z += dir.offsetZ * o;`; `onBlockActivated` -> `standardOpenBehavior(world, x, y, z, player, 0)`.
2. Add a recipe:
1. GenericRecipes machines: in the set's `registerDefaults()` add `this.register(new GenericRecipe("chem.x").setup(dur, power).inputItems(new OreDictStack(STEEL.ingot(), 2)).inputFluids(new FluidStack(Fluids.WATER, 1000)).outputItems(...).outputFluids(...));` (names unique within the set, keep the machine prefix, respect the `*Limit()` counts).

5. ## Top gotchas

Only the ones that bite most tasks; every area in `docs/codebase-map.md` has its own Gotchas list.

- `MainRegistry` has two `FMLPreInitializationEvent` handlers (`PreLoad`, `preInit`); their relative order is not guaranteed. Config is loaded inside `PreLoad` (`loadConfig()` at line ~275). Do not add cross-dependencies between the two.
- `TileMappings.put` is private: new TEs go inside `writeMappings()` (fork code repeats what `put` does from the `DBSFork.init()` hook: `TileMappings.map.put`, `TileMappings.configurables.add` for an `IConfigurableMachine`, and `Compat.blacklistAccelerator`; see the fork-code note under "Add a block"). An unregistered TE works until its chunk saves: `TileEntity.writeToNBT` throws "... is missing a mapping! This is a bug!", `AnvilChunkLoader.writeChunkToNBT` catches it per TE, logs "A TileEntity type ... It will not persist" and saves the rest of the chunk without that TE, so after a reload the block is still there but the machine's inventory and state are gone. NBT with an unknown id logs "Skipping BlockEntity with id" on load. OC-only TEs belong inside the `ocPresent` guard.
- `onChunkUnload()` overrides must call `super.onChunkUnload()`: `TileEntityLoadedBase` sets `isLoaded = false` there and `NodeNet.isBadLink` depends on it. 25 of the 48 overrides in `TileEntityLoadedBase` subclasses skip it (tracker B-061), including the ChemicalPlant, Centrifuge and Diesel exemplars; add the call when copying them.
- Net subscriptions expire after 3000 ms wall-clock (`PowerNetMK2.timeout`, `FluidNetMK2.timeout`; pneumatic 1000 ms): re-`trySubscribe` at least every 20 ticks. Destroying any node destroys its whole `NodeNet`; it re-forms next tick. `IEnergyReceiverMK2.tryUnsubscribe` is a no-op.
- `MachineDynConfig` instantiates every `IConfigurableMachine` via `newInstance()`: public no-arg ctor required, no side effects, and constructor-time reads of config statics see defaults.
- `ArmorFSB.cloneStats` shares the effects list by reference (so every `addEffect` must run before it, B-112) and re-runs `setRadResist` per piece. It does not copy `setHazardClass`/`hides`/`setOverlay`, by design: hazard classes and the overlay are read only from the helmet slot, so set them on the helmet chain, and set `hides` per piece. Hazard classes and rad resistance are filled in `PostLoad` (see Core conventions).
- `SerializableRecipe.initialize()` has no per-handler error isolation: one malformed user JSON aborts every later handler. Recipe listeners (`IRecipeRegisterListener`, which `DBSRecipes` uses) fire only when a set loads its defaults, i.e. when neither a server-synced stream nor a live `config/hbmRecipes/hbm<Machine>.json` exists. (A user `hbmPrecisionAssembly.json` does not disable expensive mode: `GeneralConfig.trueExp()` only drives the EXP HUD badge; recipes read `enableExpensiveMode` directly.)
- `BlockOre` meta is the planet (`SolarSystem.Body.ordinal()`), not a subtype: ore-dict with `oreAll()`. `CelestialBody.getBody(...)` falls back to Kerbin for unknown ids; Thatmo is unbound (no Body enum entry, `WorldGeneratorThatmo` never registered).
- QMAW manual pages require `name`, `title`, `content` AND `trigger` (use `"trigger": []`); a page without it is skipped with `[QMAW] Error reading manual`.
- Config locations: `hbm.cfg` (read once, no reload); `config/hbmConfig/` for JSON (`hbmClient/Server/Machines/CustomMachines/Fallout/ItemPools/FluidTypes/FluidTraits/Armor/RadResist.json`; underscore-prefixed files are templates and never read); `config/hbmRecipes/` for recipe JSON.
- Known upstream oddities not to "fix" blindly (they change balance or existing worlds; each is a decision row in `docs/fix-roadmap.md`): `PowerNetMK2.update` cumulative `toTransfer -= energyUsed` across priorities (B-021, D5), `OreLayer3D` using `cacheX` for the z axis (B-226, D23).
