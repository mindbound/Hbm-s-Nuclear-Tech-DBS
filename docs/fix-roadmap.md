## Principles

- One batch per change set. A batch is a set of related fixes that is tested together and sized so a session can finish it. Sessions edit the source files directly, never patch or diff files. A local session compiles with `./gradlew --offline compileJava` (`gradlew.bat` from PowerShell) before the hand-off, reports the result, leaves the change uncommitted and supplies a commit message draft; a cloud session cannot compile; it commits and pushes to its `claude/...` staging branch (the container is ephemeral; the commit message is the draft) and says the build is untested. The owner builds, tests on client and dedicated server, commits and pushes.
- Reactors, OpenComputers, saves and crashes first. The fork exists for the restored reactors, the owner develops OC-LuaJIT, and save-data or crash defects hurt most, so those phases come before cosmetic or dead-code work.
- Merge cost is a trade-off, not a rule. Every file may be edited (owner policy of 2026-09-25). JameH2 merges continue (owner decision, 2026-09-26), so each changed line in an upstream file can conflict on the next merge (hotspots in `docs/fork-notes.md`), and code in `com/hbm/dbs/` never does. Pick per change: the smallest correct edit when it is also the clearest, a larger rework (Phase 8) when it pays for itself, `com/hbm/dbs/` when the change is self-contained. Structural changes go in their own change sets so a bad merge can be reverted in one piece.
- Markers are a tracking aid. Every fix line under `src/` carries `// DBS fix B-123` (optionally followed by a short reason) on the changed line itself, not the line above, so a merge resolution that keeps the comment but takes upstream's code is visible in the diff (same rule as `docs/extending.md` section 6). Assets, deletions and files outside `src/` cannot carry one; their Status says `fixed <commit> (no-marker)`. `tools/check-fork.sh` fails after a merge when the marker of a fixed entry has disappeared, which is how an upstream merge silently undoing a fix shows up.
- The tracker is the manifest. Status is one of `open`, `fixed <commit>`, `fixed <commit> (no-marker)`, `fixed upstream <hash>` (a ported HbmMods fix, no marker), `wontfix <why>`.
- Check upstream first. Before fixing an item, look for an HbmMods fix since the merge base. The owner's clone has the read-only remotes `hbm` (HbmMods) and `upstream` (JameH2) since 2026-09-26: `git fetch hbm`, then `git log -S'<distinctive code>' hbm/master -- <file>` and `git diff 9a2eb731 hbm/master -- <file>` (a fresh clone first needs `git remote add hbm https://github.com/HbmMods/Hbm-s-Nuclear-Tech-GIT`; without it, `git log -S'<text>' HEAD -- <file>` reaches HbmMods history only up to `9a2eb731`). If HbmMods fixed it, port their hunk (it then merges cleanly) and record `fixed upstream <hash>`.
- Line numbers in the tracker come from the `22c9c89c` snapshot, which is still the state of `src/` apart from the 2026-09-26 version identity (new `com/hbm/dbs/DBSVersion.java`, `HTTPHandler` rewritten, three `ModEventHandler` lines replaced one for one); class and method names are the stable anchors, so re-read the location before editing. A fix that adds or removes lines shifts the anchors of the other entries in that file: update their line numbers in the same change set, or keep the edit line-neutral where that is just as clear (a fully qualified name instead of a new import, as the version identity did).
- Decision items are not fixed on a whim. Each "needs a decision" entry changes balance, world generation, saves or something players notice. The rows below carry a recommendation; the owner answers, the answer goes into the tracker (a `Plan:` naming a phase, or `Status: wontfix <why>`), and only then is the item worked on.

## Addon constraints when fixing

Addons in the owner's pack call or patch HBM members, and a fix that renames, retypes or moves one breaks them, often silently. The complete list is the third-party patch table in `docs/extending.md` (section 7); check it before changing any HBM member signature. The planned fixes it constrains:

- B-365 (Phase 6 after D18): clear the radiolysis map in the caller (`CrackingRecipes.registerPost`), never inside `RadiolysisRecipes.registerRadiolysis`: EnviroMine injects five radioactive-water entries at that method's HEAD. Keep the field `radiolysis` and the method's name and signature.

EndlessIDs redirects both with `require = 1` (the outer class is mixed at every startup, even with PRISM off), so removing either fails the game at startup.
- B-061, B-093, B-105 (pylons): put lifecycle code in `TileEntityCableBaseNT`, not `TileEntityPylonBase`, whose `validate`/`invalidate`/`onChunkUnload` ntmrba replaces with its own; test wire changes with ntmrba's `OPTIMIZE_WIRES` off as well, because with it on ntmrba draws the wires itself.
- B-050 and any other `BlockDummyable` change: keep `getDirModified(ForgeDirection)`, `getMetaForCore(World, int, int, int, EntityPlayer, int)` and `checkRequirement(World, int, int, int, ForgeDirection, int)`; ntmrba's `@Invoker`s crash the game when `BlockDummyable` loads if one changes. Add overloads for new parameters. B-053's optional `findCore(World, ...)` overload for older Energy Control binaries lands with B-053's own overload fix.
- B-057 (Phase 8): `getDescriptionPacket` must never return null. Angelica holds back the client ticks of every TE class that declares it until an S35 arrives.
- B-023 (D5), B-019, B-029, B-107 and any other `NodeNet` or `IFluidStandardSenderMK2` change: keep the descriptor `tryProvide(FluidType, int, World, int, int, int, ForgeDirection)` and the `HashMap<R, Long>`/`HashMap<P, Long>` fields `receiverEntries`/`providerEntries`; bobfluidtranslator patches the method and reads the fields by descriptor.
- B-410 (Phase 6, `NBTControlPacket`): keep calling `receiveControl(NBTTagCompound)`; ntmrba's lights implement only that overload.
- Sky renderer edits (none planned; B-209's fix touches only `XSatelliteRegistry`): keep the GL call order in `SkyProviderCelestial.render`/`renderSun` and `renderSun`'s signature, or Angelica's shader hooks silently move.
- Worldgen fixes (B-233, B-239 and the D23 batch): test with hodgepodge's `throttleChunkGeneration=false` too, which restores vanilla population order.

## Delivery checklist per change set

1. Re-read each item's location in the current tree and check `hbm/master` for an upstream fix (remote setup under Principles); port it if one exists.
2. Apply the fix with a `// DBS fix B-xxx` marker, or note `no-marker` for assets, deletions and files outside `src/`.
3. Local sessions: `./gradlew --offline compileJava` passes; report the result. Cloud sessions: say the build is untested.
4. Run `bash tools/check-fork.sh`.
5. Update the tracker: `Status: fixed <hash>` (filled in after the owner commits, or the staging hash), and for an answered decision row the new `Plan:` or `Status: wontfix <why>` of each entry in it.
6. Once the Status carries the hash (for local sessions, after the owner commits), run `bash tools/check-fork.sh` again; the marker check covers only entries marked fixed.
7. Hand off with the changed files, the test procedure from the phase above and a commit message draft; the owner builds, tests on client and dedicated server, commits and pushes.
8. Before a fix counts as done, the owner also launches the jar in the pack described under "Owner environment and priorities" (single-player world, all addons). `logs/fml-client-latest.log` must show no `NoSuchMethodError`, `NoSuchFieldError`, `AbstractMethodError`, `NoClassDefFoundError` or mixin failure, and no new HBM warnings. For a fix listed under "Addon constraints when fixing", also exercise the addon feature named there.
