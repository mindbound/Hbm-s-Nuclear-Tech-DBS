Provenance, working agreements and merge procedure for `mindbound/Hbm-s-Nuclear-Tech-DBS`. Facts below were verified against the cloud clone on 2026-09-24 (HEAD `ee9fd54a`; the notes were committed on top in `6a8497fb`, the `com/hbm/dbs` layout in `1277c937`, then the LF normalisation `27811a59`). Commit hashes refer to the remotes `origin` (fork), `upstream` (JameH2), `hbm` (HbmMods). The cloud clone is shallow (24 boundary commits in `.git/shallow`; HbmMods history reachable only back to 2026-06-23), so absence of a `git log -S` hit there is not proof. The 2026-09-26 revision re-measured the upstream state from the owner's local clone (full history, `upstream` and `hbm` fetched that day) and added the owner's decisions of that day and a verified inspection of the owner's mod pack (addon bytecode, mixins, config, logs).

These notes (`CLAUDE.md`, `docs/codebase-map.md`, this file) were produced on 2026-09-24 by a multi-agent survey (19 subsystem readers, each adversarially verified against source, then accuracy and completeness critics) and hand-checked afterwards. Line numbers are from that snapshot; class and method names are the stable anchors.

## Edit policy

Owner decision, 2026-09-25: all restrictions on what may be edited are lifted. Any file in the repository may be changed, including upstream-origin code (registries such as `ModItems`/`ModBlocks`/`TileMappings`/`ClientProxy`/`MainRegistry`, recipe classes, tiles), lang files and assets, `changelog`, `README.md`, `gradle.properties`, `RefStrings`, `build.gradle`, CI, `.editorconfig`, the vendored `cofh` API, the docs and `tools/`. Refactors, deletions, renames and new libraries are allowed. No upstream pull requests are planned, so upstream's contribution rules do not apply. This supersedes the edit restrictions of earlier revisions of this file and of `docs/` (the "keep fork changes additive" and "never inline" guidance, the former "small diffs by default" principle of `docs/fix-roadmap.md` and "fixes go through the fork-owned package" of `docs/known-bugs.md`); the current docs no longer contain them.

What remains:

- Technical rules that hold regardless of policy, because breaking them breaks the game, not a merge: registration order (`MainRegistry` lifecycle; hazard classes and rad resistance are filled in `PostLoad` from entries that `ArmorFSB` pieces queue when they are constructed, which overwrites earlier same-key writes; the tables stay writable afterwards and later writes win), persisted positional IDs (append-only; list in `CLAUDE.md`), side discipline, `serialize`/`deserialize` order, LF line endings, `I18nUtil` over the client-only `I18n`, optional mods behind `Loader.isModLoaded`/`@Optional`, and the HBM members that addons in the owner's pack call or patch (see "Addons in the owner's pack that depend on HBM internals").
- Merge cost as a trade-off: because the fork keeps merging JameH2's branch, an edit in a file upstream also touches can conflict (hotspots under "Direct HbmMods merge" below), and code in `com/hbm/dbs/` never does. That is a reason to prefer one placement over another when both are equally clean, not a prohibition. The merge procedures below stay valid; after a merge, `tools/check-fork.sh` plus `git diff` of the conflicted files show what needs re-checking.
- The `// DBS fix B-xxx` marker on tracker fixes: a tracking aid so `tools/check-fork.sh` can detect a merge that silently undid a fix.
- The working agreement on commits (sessions draft, the owner reviews and pushes), below.

## OC-LuaJIT relation

`C:\Users\astro\Downloads\OC-LuaJIT` on the owner's machine, `/home/user/OC-LuaJIT` in the cloud (`github.com/mindbound/OC-LuaJIT`, modid `ocluajit`) adds a LuaJIT CPU architecture to GTNH OpenComputers by subclassing OC's `NativeLuaArchitecture` (overriding `factory`, `initialize`, `save`, `load`; `LuaStateLuaJIT` redeclares natives with no behavioural overrides). It compiles against GTNH OC 1.12.58 (`dependencies.gradle:39`) and links cleanly against 1.12.62, the owner's runtime: every `li/cil/oc` reference of its 7 classes resolves there (verified 2026-09-26). It never references HBM, and HBM references only `li.cil.oc.api.*` (compileOnly `com.github.MightyPirates:OpenComputers:1.7.10-forge~1.8.9:api`); all 22 of HBM's OC member references resolve against 1.12.62 with identical descriptors. The two meet only at OC's component-call boundary, which OC-LuaJIT inherits unchanged, so HBM component code needs no changes for it. Two things to keep in mind:

- OC-LuaJIT is a 5.2-class VM. The shipped floppy `assets/hbm/disks/pwrangler/usr/bin/PWRangler.lua` uses Lua 5.3 floor division `//` (lines 207, 213, 217, 252, 256) and would not load there; the disks README's "preferably Lua 5.3" advice conflicts with that target. The owner's instance defaults new CPUs to Lua 5.3 (`OpenComputers.cfg` `defaultLua53=true`), so the `//` matters only on CPUs switched to Lua 5.2, LuaJ (registered in that instance) or OC-LuaJIT (B-317).
- HBM emits no OC signals, so OC-LuaJIT's ocelot-brain signal-marshalling defect (the `Integer` signal-loss item in OC-LuaJIT's own `docs/roadmap.md`, L76-80, not this repo's `docs/fix-roadmap.md`) cannot affect HBM. The three marshalling-sensitive HBM spots (`args.checkTable` integer keys, `checkAny == null`, mixed boxed numeric returns) behave identically under both VMs.
