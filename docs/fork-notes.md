# Fork notes

Provenance, working agreements and merge procedure for `mindbound/Hbm-s-Nuclear-Tech-DBS`. Facts below were verified against the cloud clone on 2026-09-24 (HEAD `ee9fd54a`; the notes were committed on top in `6a8497fb`, the `com/hbm/dbs` layout in `1277c937`, then the LF normalisation `27811a59`). Commit hashes refer to the remotes `origin` (fork), `upstream` (JameH2), `hbm` (HbmMods). The clone is shallow (24 boundary commits in `.git/shallow`; HbmMods history reachable only back to 2026-06-23), so absence of a `git log -S` hit is not proof.

These notes (`CLAUDE.md`, `docs/codebase-map.md`, this file) were produced on 2026-09-24 by a multi-agent survey (19 subsystem readers, each adversarially verified against source, then accuracy and completeness critics) and hand-checked afterwards. Line numbers are from that snapshot; class and method names are the stable anchors.

## Edit policy

Owner decision, 2026-09-25: all restrictions on what may be edited are lifted. Any file in the repository may be changed, including upstream-origin code (registries such as `ModItems`/`ModBlocks`/`TileMappings`/`ClientProxy`/`MainRegistry`, recipe classes, tiles), lang files and assets, `changelog`, `README.md`, `gradle.properties`, `RefStrings`, `build.gradle`, CI, `.editorconfig`, the vendored `cofh` API, the docs and `tools/`. Refactors, deletions, renames and new libraries are allowed. No upstream pull requests are planned, so upstream's contribution rules do not apply. This supersedes the edit restrictions of earlier revisions of this file and of `docs/` (the "keep fork changes additive" and "never inline" guidance, the former "small diffs by default" principle of `docs/fix-roadmap.md` and "fixes go through the fork-owned package" of `docs/known-bugs.md`); the current docs no longer contain them.

What remains:

- Technical rules that hold regardless of policy, because breaking them breaks the game, not a merge: registration order (`MainRegistry` lifecycle; hazard classes and rad resistance are filled in `PostLoad` from entries that `ArmorFSB` pieces queue when they are constructed, which overwrites earlier same-key writes; the tables stay writable afterwards and later writes win), persisted positional IDs (append-only; list in `CLAUDE.md`), side discipline, `serialize`/`deserialize` order, LF line endings, `I18nUtil` over the client-only `I18n`, optional mods behind `Loader.isModLoaded`/`@Optional`.
- Merge cost as a trade-off: while the fork keeps merging JameH2's branch, an edit in a file upstream also touches can conflict (hotspots under "Direct HbmMods merge" below), and code in `com/hbm/dbs/` never does. That is a reason to prefer one placement over another when both are equally clean, not a prohibition. The merge procedures below stay valid; after a merge, `tools/check-fork.sh` plus `git diff` of the conflicted files show what needs re-checking.
- The `// DBS fix B-xxx` marker on tracker fixes: a tracking aid so `tools/check-fork.sh` can detect a merge that silently undid a fix.
- The working agreement on commits (sessions draft, the owner reviews and pushes), below.

## Upstream-merge procedure

### Routine: merge JameH2's tip

Whether the fork keeps merging JameH2's branch at all is still pending (`docs/extending.md` decision 1; recommendation: keep merging for now). If it does, the normal path is: JameH2 absorbs HbmMods and the fork only follows JameH2.

1. `git fetch upstream`; `git log --oneline HEAD..upstream/space-travel-twopointfive` shows what arrives.
2. From a clean working tree, `git merge --no-ff --no-commit -Xrenormalize upstream/space-travel-twopointfive`; after resolving any conflicts run `git add --renormalize .`, check that `git ls-files --eol | grep -E 'i/(crlf|mixed)'` prints nothing, then `git commit`. `-Xrenormalize` is mandatory since the LF normalisation `27811a59`: upstream is still CRLF in ~580 files and ours are LF, so without it every such file upstream touched conflicts wholesale (`git config merge.renormalize true` makes it the clone's default). It only normalises files both sides changed, though: files upstream adds, and files only upstream changed (e.g. `ClientProxy.java` CRLF flips), arrive as upstream's CRLF blobs, because a merge writes the index directly and `.gitattributes` never runs on them. `git add --renormalize .` converts them before the merge commit (it leaves unmerged paths alone, but re-adds every other tracked file from disk, hence the clean tree). Only the fork's own lines can conflict: the two `// DBS fork hook` lines (`main/MainRegistry.java` after `ModItems.mainRegistry()`, `main/NEIRegistry.java`), the two lang edits (`lang/en_US.lang`, `lang/de_DE.lang`), `.editorconfig` (fork line 5 against HbmMods' pending 17-line extension; keep `end_of_line = lf`), a modify/delete on `CONTRIBUTING.md` if upstream edits it (keep it deleted), and an add/add on `handler/nei/BreederRecipeHandler.java`, `com/hbm/dbs/*`, `tools/check-fork.sh` or `.gitattributes` only if upstream ever creates a file of the same name (plus `changelog` if a Space note was added). Any fork edit made inline in an upstream file since then (allowed by the 2026-09-25 edit policy) can conflict too; `git diff --ignore-cr-at-eol --stat 64b64130 HEAD` lists them. Keep the fork hunks unless upstream deleted the restored classes. The first step needs the remote: `git remote add upstream https://github.com/JameH2/Hbm-s-Nuclear-Tech-GIT` (the owner's local clone has only `origin`).
3. Run `bash tools/check-fork.sh` (Git Bash on Windows). It checks the fork-owned files, the two hook lines, the listener API and the two recipe-set class names it dispatches on, the restored recipes (and that no duplicate of them exists elsewhere: a duplicate id throws inside `GenericRecipes.register` after the recipe was already appended, `DBSRecipes` catches and logs it as "[DBS] Failed to register fork recipes", and the machine ends up with a duplicate entry while the remaining fork recipes of that set are skipped), every upstream class, registration and TESR the restores depend on, and that " (LEGACY)" was not reintroduced in `en_US`/`de_DE`. It also fails on unresolved conflict markers (in `src/main/java`, the lang files, `tools/`, `CLAUDE.md` and `docs/`), on a `.gitattributes` without the `*.java text eol=lf` rule, on any CRLF or mixed-ending file in the index (its message says to merge with `-Xrenormalize`; if you did, `git add --renormalize .` from step 2 is the fix), and on any tracker entry whose `Status: fixed ...` (without `no-marker`) has lost its `// DBS fix B-xxx` marker; it prints a note when `merge.renormalize` is unset. Expect the `@Deprecated` markers from `54642452`/`1abaa1e5` to arrive the first time JameH2 merges a build >= 5808; they are inert (keep or delete them as you like). `13b8efef` (waste plates hidden from creative) is neutralised by `DBSItems.afterItemInit()`.
4. Hand off for a local `./gradlew build` and in-game test. By default `gradle.properties`/`RefStrings` follow JameH2 and nothing is bumped; the fork may set its own version at any time (see "Merge hazards" for the update-check coupling).

## Merge hazards and working agreements

- Never insert into or reorder the persisted positional lists (`EnumAmmo` and the other enum-multi ordinals, `BulletConfig` ids, Fluids IDs, `Mats` ids and the rest of the list in `CLAUDE.md`): that breaks existing saves, whatever the edit policy. The sync-only positional lists (packet discriminators, `CelestialBodyTrait` indices, mod-entity ids, `EnumKeybind`) only break a client and server running different jars. Reordering or rewriting ordinary registries is allowed; while upstream merges continue, expect conflicts in proportion. ## Working agreement and cloud / local split

- Roles: either the owner or a session makes code changes. Sessions always edit the source files directly (owner decision, 2026-09-25); they never produce patch or diff files for the owner to apply. A session provides a commit message draft for its own changes. The owner reviews everything and pushes `space-travel-twopointfive` themselves; sessions never push to it.
- Local session (Claude Code on the owner's machine; `JAVA_HOME` JDK 1.8.0_211, Temurin 8u462 on PATH, JDK 17 installed, JDK 21/25 only as Gradle toolchains): edit the working tree, do not commit; run `./gradlew --offline compileJava` before handing off code changes and report the result; put the draft commit message in the hand-off. Forge/FML sources and `javap` on the deobfuscated Forge jar are available for vanilla questions (paths in `CLAUDE.md`, "Build and test"). The owner builds the jar, tests on client and dedicated server, commits and pushes.
- Cloud session: the container is ephemeral, so work is committed and pushed to the session's `claude/...` branch as a staging area, and that commit message is the draft. The owner reviews the branch, merges or cherry-picks into `space-travel-twopointfive` (squash and reword as they like), and pushes.

- Cloud sessions: JDK 21 only, and the network policy blocks every Forge/NTM maven host (`maven.ntmr.dev`, `maven.minecraftforge.net`, `files.minecraftforge.net`, `libraries.minecraft.net`, `modmaven.dev`, `jitpack.io`, `cursemaven.com`, `gregtech.mechaenetia.com`); only `repo1.maven.org`, `plugins.gradle.org`, `services.gradle.org`, `github.com`, `raw.githubusercontent.com` are allowed. The mod cannot be compiled here until the allowlist is widened (and JDK 8 installed; apt candidate `openjdk-8-jdk` 8u482 exists).
- Therefore cloud sessions write code, docs and grep-level verification; the owner (or a local session) compiles (`./gradlew build`, JDK 8) and the owner tests on client and dedicated server locally at `C:\Users\astro\Downloads\Hbm-s-Nuclear-Tech-DBS`. Every cloud hand-off should state what was not compiled.
- There are no automated tests. CI only runs on `space-travel-twopointfive`, so cloud branches get no CI, and GitHub Actions had never run on the fork as of 2026-09-24 (not checkable from a local clone). A CI build would be versioned `X<days since 2010-10-10>` (e.g. 5829 on 2026-09-25), not `X5778`, because `build.yml` rewrites both `RefStrings.VERSION` and `mod_build_number`. Enabling Actions in the fork's repository settings would build a jar for every push to `space-travel-twopointfive` on Temurin JDK 8 and upload `build/libs` as an artifact; adding `claude/**` or `workflow_dispatch` to the workflow's `on:` block would extend that to staging branches.
- Line endings: the index is all-LF (`27811a59`) and `.gitattributes` normalises on commit. The owner's Windows working tree is still CRLF on disk for most files (`core.autocrlf=true` from the Git for Windows system config; git did not rewrite unchanged files when the attributes arrived), which does not affect commits. A one-time refresh to LF on disk, on a clean tree only: `git rm -r --cached -q . && git reset --hard` (owner's call; it discards uncommitted changes).
- No ForgeGradle workspace exists in the cloud (no `eclipse/`, no `~/.gradle/caches/minecraft`), so decompiled Minecraft/Forge sources cannot be read: reason about vanilla/Forge methods from memory or from how this repo's callers use them, and flag every such assumption in the hand-off for local verification.

## OC-LuaJIT relation

`C:\Users\astro\Downloads\OC-LuaJIT` on the owner's machine, `/home/user/OC-LuaJIT` in the cloud (`github.com/mindbound/OC-LuaJIT`, modid `ocluajit`) adds a LuaJIT CPU architecture to GTNH OpenComputers 1.12.58 by subclassing OC's `NativeLuaArchitecture` (overriding `factory`, `initialize`, `save`, `load`; `LuaStateLuaJIT` redeclares natives with no behavioural overrides). It never references HBM, and HBM references only `li.cil.oc.api.*` (compileOnly `com.github.MightyPirates:OpenComputers:1.7.10-forge~1.8.9:api`). The two meet only at OC's component-call boundary, which OC-LuaJIT inherits unchanged, so HBM component code needs no changes for it. Two things to keep in mind:

- OC-LuaJIT is a 5.2-class VM. The shipped floppy `assets/hbm/disks/pwrangler/usr/bin/PWRangler.lua` uses Lua 5.3 floor division `//` (lines 207, 213, 217, 252, 256) and would not load there; the disks README's "preferably Lua 5.3" advice conflicts with that target.
- HBM emits no OC signals, so OC-LuaJIT's ocelot-brain signal-marshalling defect (the `Integer` signal-loss item in OC-LuaJIT's own `docs/roadmap.md`, L76-80, not this repo's `docs/fix-roadmap.md`) cannot affect HBM. The three marshalling-sensitive HBM spots (`args.checkTable` integer keys, `checkAny == null`, mixed boxed numeric returns) behave identically under both VMs.
